# Quy tắc tạo bảng (Entity + EF Core Configuration)

Đúc kết từ 25 entity + 20 file Configuration đang có trong `Depot.Data`. Áp dụng mỗi khi thêm bảng mới
(vd. Billing, Cleaning, Department, Yard mở rộng...). Đây là tài liệu con của
[00-quy-tac-backend.md](00-quy-tac-backend.md) mục 5.

> **Đổi quy tắc kể từ mục 2 & 8 dưới đây:** bảng **MỚI** tạo từ giờ trở đi dùng khóa chính `long` và
> liên kết sang bảng khác bằng `Code` (không dùng Id làm FK). **25 bảng hiện có (Guid/int, FK theo Id)
> giữ nguyên, không đổi** — đã build/migrate/seed xong, đổi lại là việc phá dữ liệu, phải hỏi trước khi
> làm (xem quy tắc chung mục 7). Hai quy tắc key khác nhau cùng tồn tại trong 1 database là chủ đích,
> không phải sai sót — mục 2 và mục 8 nêu rõ khi nào dùng kiểu nào.

## 1. Entity luôn kế thừa `FullAuditedEntity<TKey>`

```csharp
public class MyNewEntity : FullAuditedEntity<long>   // bảng MỚI: luôn long — xem mục 2
```

Base class (`Depot.Data/Entities/Base/FullAuditedEntity.cs`) đã có sẵn `Id, CreatedAt, CreatedBy,
LastModifiedAt, LastModifiedBy, IsDeleted, DeletedAt, DeletedBy` — **không khai báo lại** các field này.

## 2. Chọn kiểu khóa chính

| Kiểu | Dùng cho | Ví dụ |
|---|---|---|
| `long` | **Mọi bảng MỚI tạo từ giờ trở đi**, không phân biệt loại nghiệp vụ | Billing, Cleaning, Department, Yard Zone/Block/Forklift... |
| `Guid` | Legacy — 15 bảng giao dịch đã có, giữ nguyên | `DepotJob, Survey, Estimate, RepairOrder, Payment, ServiceOrder, JobAuditLog, CustomerCompany, CustomerBooking...` |
| `int` | Legacy — 5 bảng danh mục/hệ thống đã có, giữ nguyên | `SystemUser, Role, Company, ShippingLine, YardPosition` |

`Id` kiểu `long` map sang Postgres `bigint`, EF Core tự tạo cột tự tăng
(`GENERATED BY DEFAULT AS IDENTITY`, tương đương `bigserial`) — không cần cấu hình gì thêm ngoài khai
báo kiểu property, `ValueGeneratedOnAdd()` là convention mặc định cho khóa số nguyên.

`Id` chỉ dùng làm khóa nội bộ của chính bảng đó (định danh hàng, thứ tự tạo) — **không dùng `Id` để
bảng khác liên kết tới**, xem mục 8b.

## 3. Vị trí file & namespace

```
Depot.Data/Entities/<Nhóm>/<TenEntity>.cs
```

Nhóm hiện có: `System, Master, Depot, Finance, Inventory, Yard, Integration`. Chọn đúng nhóm theo nghĩa
nghiệp vụ (Billing/Cleaning → `Finance` hoặc nhóm mới cùng cấp nếu không khớp nhóm nào, không dồn vào
`Depot` cho mọi thứ). Viết XML `/// <summary>` tiếng Việt cho entity và **từng property** — giữ đúng văn
phong đang có trong toàn bộ codebase.

## 4. Luôn tạo file Configuration riêng

```
Depot.Data/Configurations/<TenEntity>Configuration.cs
```

```csharp
public sealed class MyNewEntityConfiguration : IEntityTypeConfiguration<MyNewEntity>
{
    public void Configure(EntityTypeBuilder<MyNewEntity> builder)
    {
        builder.Property(x => x.Code).IsRequired().HasMaxLength(40);
        builder.HasIndex(x => x.Code).IsUnique();
        builder.Property(x => x.Amount).HasPrecision(18, 2);
        // Liên kết theo Code, không theo Id — chi tiết xem mục 8b
        builder.HasOne(x => x.Customer)
            .WithMany()
            .HasForeignKey(x => x.CustomerCode)
            .HasPrincipalKey(x => x.Code)
            .OnDelete(DeleteBehavior.Restrict);
    }
}
```

Bắt buộc tạo file này khi entity có: business key cần unique, FK cần khai báo quan hệ/OnDelete, hoặc
field cần giới hạn độ dài/precision. **Không** thêm cấu hình mới vào `DepotDbContext.OnModelCreating`
— khối `modelBuilder.Entity<X>().Property(...).HasPrecision(...)` trong đó là tech-debt cũ (dùng cho
`DamageItem, EstimateItem` — 2 entity không có DbSet/Configuration riêng vì chỉ truy cập qua collection
nav của cha), không nhân rộng thêm theo cách đó.

`DepotDbContext.OnModelCreating` tự động quét mọi Configuration qua
`modelBuilder.ApplyConfigurationsFromAssembly(...)` — chỉ cần tạo file, không cần đăng ký tay.

## 5. Tên bảng

**Mặc định KHÔNG gọi `.ToTable(...)`** — để EF tự đặt tên = PascalCase số nhiều theo tên `DbSet`
(vd `CustomerBookings`, `ServiceOrders`, `Payments`). Đây là convention của **24/25 bảng hiện có**.

> Ngoại lệ lịch sử: `DepotJob` có `.ToTable("depot_jobs")` (snake_case) — là điểm không nhất quán có
> sẵn từ trước, **không sửa lại** (đổi tên bảng đã có dữ liệu là việc phá migration, phải hỏi trước khi
> làm — xem mục 7 của quy tắc chung). Bảng mới không theo mẫu này.

## 6. Kiểu dữ liệu & giới hạn cột

| Loại field | Kiểu C# | Cấu hình |
|---|---|---|
| Business code/key (JobNo, OrderNo, Code) | `string` | `IsRequired().HasMaxLength(n)` — tham khảo độ dài hiện có: `JobNo 30, ContainerNo 15, OrderNo 40, Code 20–50` tuỳ ngữ cảnh |
| Status (string enum) | `string` | `IsRequired().HasMaxLength(20–50)`, giá trị UPPER_SNAKE_CASE (xem quy tắc chung mục 4) |
| Text tự do (notes, address, description) | `string?` | không set `HasMaxLength` → map `text`, không giới hạn |
| Tiền tệ / số lượng / đơn giá | `decimal` | luôn `HasPrecision(18, 2)` khai báo trong Configuration của chính entity |
| Ngày giờ | `DateTime` / `DateTime?` | lưu UTC, Postgres tự map `timestamp with time zone` |
| Cờ boolean | `bool` | mặc định giá trị rõ ràng, vd `= false` |

## 7. Index

- Mọi business key duy nhất → `builder.HasIndex(x => x.Code).IsUnique();`
- Bảng legacy (Guid/int): mọi cột FK (`XxxId`) → `builder.HasIndex(x => x.XxxId);` (khai báo tường minh
  dù `HasForeignKey` đã ngầm tạo index, để dễ đọc và nhất quán với `DepotJobConfiguration`).
- Bảng mới: mọi cột FK dạng code (`XxxCode`) → cũng phải có index tường minh
  `builder.HasIndex(x => x.XxxCode);` — bắt buộc vì FK theo string chậm hơn FK theo số nếu thiếu index,
  xem mục 8b.
- Cột hay lọc/tìm kiếm (Status, ContainerNo, ngày tháng dùng filter theo khoảng) → thêm index không unique.

## 8. Quan hệ & `OnDelete`

| Loại quan hệ | Ví dụ | OnDelete |
|---|---|---|
| 1-1 "chi tiết thuộc về" 1 DepotJob (con sinh ra, xoá cha thì xoá theo) | `DepotJob → Survey/Estimate/RepairOrder/Payment`, `DepotJob → AuditLogs` | `Cascade` |
| N-1 tới bảng danh mục dùng chung (không được xoá cha nếu đang bị tham chiếu) | `DepotJob → ShippingLine`, `ServiceOrder → Material` | `Restrict` |
| Dòng con thuần tuý của 1 aggregate (không cần DbSet riêng, chỉ qua collection nav) | `Estimate → EstimateItem`, `ServiceOrder → ServiceOrderItem`, `Survey → DamageItem` | `Cascade` |

Bảng dòng con kiểu `EstimateItem/DamageItem` **không cần thêm `DbSet<T>` riêng** trong `DepotDbContext`
nếu ứng dụng chỉ bao giờ truy cập nó qua `parent.Items`/`parent.Damages` — chỉ thêm `DbSet` khi cần
query độc lập bảng đó (lọc/thống kê trực tiếp không qua cha).

Bảng trên đây (mục 8) mô tả quy tắc FK theo **Id** — chỉ áp dụng cho 25 bảng legacy đã có. Bảng mới
dùng quy tắc FK theo **Code** ở mục 8b.

## 8b. Liên kết giữa các bảng MỚI: dùng `Code`, không dùng `Id`

Từ giờ trở đi, khi 1 bảng mới cần tham chiếu tới 1 bảng khác (mới hoặc legacy), cột FK lưu **giá trị
`Code`/business key** của bảng cha (kiểu `string`), không lưu `Id`/`Guid`.

**a) Bảng mới → bảng mới:** cột FK đặt tên `<TenBangCha>Code`, kiểu `string`, cấu hình alternate key vì
FK không trỏ vào PK mặc định của EF:

```csharp
public class Customer : FullAuditedEntity<long>
{
    public string Code { get; set; } = string.Empty;   // business key, bảng khác liên kết vào đây
    ...
}

public class Invoice : FullAuditedEntity<long>
{
    public string Code { get; set; } = string.Empty;
    public string CustomerCode { get; set; } = string.Empty;  // FK — lưu Code, không lưu CustomerId
    public virtual Customer? Customer { get; set; }
}
```

```csharp
// InvoiceConfiguration
builder.HasOne(x => x.Customer)
    .WithMany()
    .HasForeignKey(x => x.CustomerCode)
    .HasPrincipalKey(x => x.Code)     // bắt buộc — báo EF FK trỏ vào Code, không phải Id
    .OnDelete(DeleteBehavior.Restrict);
```

**b) Bảng mới → bảng legacy (Guid/int):** không có `Code` kiểu long để trỏ vào, và không được đổi PK
bảng legacy — dùng đúng business key sẵn có của bảng legacy đó làm cột FK string, **không khai báo quan
hệ điều hướng `HasOne/WithMany` bắt buộc** (vì PK bảng legacy khác kiểu, alternate key phải cùng CLR
type phía nguyên bản mới match chuẩn) — chỉ lưu cột string + index, coi là liên kết logic, kiểm tra tồn
tại ở tầng Service khi ghi dữ liệu:

| Bảng legacy | Business key dùng để liên kết |
|---|---|
| `DepotJob` | `JobNo` hoặc `ContainerNo` |
| `ShippingLine` | `Code` |
| `Material` | `Code` (kiểm tra field thật trong entity trước khi dùng) |
| `CustomerCompany` | `Code` |

```csharp
public class CleaningRecord : FullAuditedEntity<long>
{
    public string Code { get; set; } = string.Empty;
    public string JobNo { get; set; } = string.Empty;   // liên kết logic sang DepotJob.JobNo
}
```

```csharp
// CleaningRecordConfiguration
builder.Property(x => x.JobNo).IsRequired().HasMaxLength(30);
builder.HasIndex(x => x.JobNo);
// Không HasForeignKey sang DepotJob — Service tự validate JobNo tồn tại trước khi ghi.
```

**Lý do đổi quy tắc:** Code là định danh nghiệp vụ ổn định, dễ đọc/debug, không phụ thuộc kiểu khóa nội
bộ (Guid/int/long) của từng thế hệ bảng — phù hợp khi hệ thống có nhiều đợt phát triển với quy ước Id
khác nhau như hiện tại. Đánh đổi: JOIN theo string chậm hơn JOIN theo số — luôn phải có index trên cột
Code/FK-code (mục 7), và **Code phải bất biến** sau khi tạo (không cho sửa Code của bản ghi đã bị bảng
khác tham chiếu — validate ở Service).

## 9. Sau khi entity + configuration xong

```powershell
dotnet ef migrations add <TenMoTaHanhDong> --project "Depot.Data" --startup-project "Depot.BackendApi"
```

- Đặt tên migration PascalCase, mô tả hành động ngắn gọn (vd `AddCleaningModule`,
  `AddYardZoneAndForklift`) — không dùng tên chung chung như `Update1`.
- **Không sửa tay** file migration đã tạo, không sửa tay schema trên DB.
- Migration chạy tự động khi API khởi động qua `DbInitializer.InitializeAsync` (`Program.cs`) — build
  thành công (`dotnet build`) chưa đủ để xác nhận đúng, cần chạy thử API với Postgres thật để migration
  áp dụng.

## 10. Checklist nhanh cho 1 bảng mới

- [ ] Kế thừa `FullAuditedEntity<long>` (mục 1, 2) — KHÔNG dùng Guid/int cho bảng mới
- [ ] Có cột `Code` (string, unique) làm business key để bảng khác liên kết tới (mục 8b)
- [ ] Đặt đúng thư mục nhóm nghiệp vụ (mục 3), comment tiếng Việt đầy đủ
- [ ] Có file `Configuration` riêng nếu có ràng buộc (mục 4) — không sửa `OnModelCreating`
- [ ] Không gọi `.ToTable()` trừ khi có lý do đặc biệt đã xác nhận trước (mục 5)
- [ ] Business key có `HasMaxLength` + unique index (mục 6, 7)
- [ ] Field tiền tệ có `HasPrecision(18, 2)` (mục 6)
- [ ] FK sang bảng MỚI khác: cột `<Ten>Code` (string) + `HasPrincipalKey(x => x.Code)` + index +
      `OnDelete` (mục 7, 8b) — không dùng `<Ten>Id`
- [ ] FK sang bảng LEGACY (Guid/int): cột string lưu business key sẵn có của bảng đó (`JobNo`, `Code`...)
      + index, validate tồn tại ở Service, không ép `HasForeignKey` khác kiểu khóa (mục 8b)
- [ ] Chỉ thêm `DbSet<T>` trong `DepotDbContext` nếu cần query độc lập (mục 8)
- [ ] Tạo migration mới bằng `dotnet ef migrations add`, không sửa tay (mục 9)
- [ ] Nếu entity mới cần Controller → nhớ đăng ký Service vào DI ở `Program.cs`
      (xem [00-quy-tac-backend.md](00-quy-tac-backend.md) mục 1 — lỗi đã gặp thực tế)
